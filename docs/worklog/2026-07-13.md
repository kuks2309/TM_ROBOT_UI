## 1. 개요

## 2. Vision 실시간성 — 병목 실측 (진단)
- **원인**: 1Hz 는 타이머 한계가 아님. 기존 GUI 타이머는 500ms(2 FPS 목표)인데(`main_window.py:911-928`), **매 프레임이 "명령→촬영→전송→디코드" 왕복 전체**를 재수행하므로 왕복 시간이 실효 속도를 결정. TM 내장 카메라는 **트리거 방식**(스트리밍 아님).
- **실측 분해**(무이동 연속 6회, 기가비트 유선):
  | 구간 | 시간 | 비중 |
  | --- | --- | --- |
  | send_script 응답 | ~3ms | 0.6% |
  | 네트워크 전송(1.5MB) | ~13ms | 2.5% |
  | PC 디코드+발행 | ~90ms | 17% |
  | **로봇측(안정화+촬영+인코딩)** | **~410ms** | **80%** |
- **핵심**: 로봇이 보내는 건 raw 15MB 가 아니라 **인코딩된 1.5MB** → 기가비트에서 13ms 면 전송 끝. **네트워크·이미지 크기는 전송 병목이 아님**. PC 최적화로 못 줄이는 **로봇 내부가 80%**.
- **개선 적용**: TMflow "로봇 안정화를 위한 유휴 시간" 축소([TMvision v2.18 (KR) p.28](../Software_TMvision_2.18_1.00_KR.pdf)) → **0.580s→0.515s, 1.71→1.93 FPS(+13%)**. 도움은 되나 주범 아님.
- **천장**: 설정 레버를 다 써도 3~4 FPS. **30 FPS 는 별도 스트리밍 카메라 없이는 불가**.
- **캘리브 충돌**: 해상도를 낮추면 속도↑ 하지만 2026-07-10 완료한 intrinsic(2592×1944 기준, 0.4575px)이 **무효화**됨 → 현재는 **풀해상도 유지** 권고.
- 보고서: `docs/vision/realtime-camera-report-2026-07-13.md`

## 3. 웹 GUI 라이브 뷰 구현
- **백엔드**: `bridge_node.capture_still()` 신규 — `Vision_DoJob("<잡>")` **무이동** 촬영. `api.py` 에 `POST /vision/snap` 추가.
  - **모션 게이트 없음**(의도적). 근거: [TMscript v2.18 Rev1.0 §13.26, p.351-352](../Programming-Language-TMscript_2.18_Rev1.0_EN.pdf) — 초기위치 잡이면 실행 거부(False)이므로 **구조적으로 로봇 이동 불가**. 실측 검증: 연속 촬영 4회 TCP 최대 편차 **0.0038mm / 0.0004°**(반복정밀도 노이즈 범위) = 실이동 0.
  - 기존 `capture_vision`(`Vision_DoJob_PTP` = 이동)은 **게이트 유지**.
- **프론트**: `bridgeClient.snapVision()` + `Vision.tsx` 에 `▶ 라이브 시작` 토글, **실측 FPS 칩**, 워치독(3초 무프레임 시 재시동).
  - **자가 클럭(self-clocking)**: 고정 타이머로 쏘면 왕복(~0.5s)보다 빨라 요청 적체 → **프레임 도착 시 다음 촬영 예약**해 달성 가능한 최대 속도로 수렴.
- 검증: `tsc --noEmit` exit 0, 잡명 인젝션 차단 확인, 무이동 확인, **사용자 웹 실테스트 통과**.
- 파일: `src/tm_web_bridge/tm_web_bridge/{bridge_node.py,api.py}`, `~/Desktop/TRobotics_Client/src/{api/bridgeClient.ts,main/pages/tabs/Vision.tsx}`

## 6. ⚠️ 검증 도구가 헛돌고 있었음 (중대)
- **`npx tsc --noEmit` 이 아무 파일도 검사하지 않았다** — `tsconfig.json` 이 solution 스타일(`"files": []` + references)이라 **항상 exit 0**. 이 세션 내내 이걸 근거로 "타입체크 통과"를 반복 보고했으나 **헛검증**이었다.
- 올바른 명령은 **`npx tsc -b`** (= `package.json` 의 `build` 가 이미 쓰던 것). 실제로 JogPanel 추출 중 `motionEnabled` 선언을 지워 **시퀀스 실행 버튼이 깨졌는데**(TS2304 2건) 가짜 검사는 통과시켰고, `tsc -b` 로 즉시 검출·복구했다.
- 기록: `docs/claude-mistake/2026-07-13-001.md` (`rule-violation`/`verify-skip`). 재발 방지로 **매 세션 자동 주입되는 프로젝트 메모리에 정규 검증 명령을 명시**.
- 유사 함정: 카메라 로그(`print()`)의 **블록 버퍼링** 탓에 프레임 계수가 밀려("0→0→37") 오진할 뻔 → **토픽 직접 구독 계수**로 교체해 확정.

## 7. 복수 기기 라이브 병목 → 서버 단일 촬영 루프 (핵심)
- **진단**: 라이브 트리거가 **클라이언트 자가 클럭**이라 기기 N대 = **로봇 촬영 N배** → 로봇 명령 큐 포화 → 같은 채널을 쓰는 **조그가 뒤에 적체**. (브리지 `capture_still` 에 락·레이트리밋 전무. 네트워크 문제 아님 — 브리지 로컬 응답 2ms)
- **해결**: 트리거를 **서버로 이관**. 브리지에 시청자 관리(TTL 5초 하트비트) + **촬영 루프 1개**(`_live_running` 플래그) + **조그 우선권**(`_jog_lock` 잡히면 촬영 양보). 엔드포인트 `/vision/live/{join,leave,status}` 신설. 웹은 자가클럭 제거하고 `join` 하트비트만, **이미지는 기존 pub/sub 구독 유지** → 여럿이 봐도 촬영 1배, **아무도 안 쫓아냄**(2명 이상이면 `👥 N명 시청 중` 표시).
- **검증**: 토픽 직접 계수 — **시청자 1명 1.20 FPS / 3명 1.29 FPS (거의 동일)** = 로봇 부하가 시청자 수와 무관. 루프 시작 5/종료 5(잔존 0), 촬영 실패 0, 클럭 경고 0. `tsc -b` 0 errors, `vite build`·`colcon build` 성공. **사용자 복수 기기 실기 확인 완료.**
- **구현 중 자체 버그 2건 수정**: ① 루프 생존을 `Thread.is_alive()` 로 판정해 `leave`→`join` 사이 **경합으로 루프 0개**가 되는 버그(실측 0장 재현) → **락 보호 `_live_running`** 로 종료·시작 결정을 직렬화 ② `jpeg_republish` 죽으면 클럭이 끊겨 **조용히 느려짐** → 타임아웃 시 경고 로그 추가.
- 상세: `issues_and_fixes.md` 2026-07-13.

## 8. 시스템 자원 문제 2건

## 10. TM20 로봇 모델(URDF) 확보 — MoveIt 블로커 해소 (핵심)
- **블로커였던 것**: 기록상 로봇은 TM250250 인데 워크스페이스에 TM25/TM20/TM16 URDF 가 0건. **URDF 가 실물과 다르면 충돌 모델이 틀려 오히려 위험**하므로 MoveIt 착수 불가였다.
- **해소**: 사용자가 실물을 **TM20M** 으로 확인. 확인해 보니 업스트림 [TechmanRobotInc/tmr_ros2](https://github.com/TechmanRobotInc/tmr_ros2) `humble` 의 `tm_description` **v1.2.0** 에 tm16·tm20 이 **이미 존재** — 로컬 사본이 **v1.1.1(추가 이전 구버전)** 이었을 뿐. 새로 만들 필요 없었다.
- **숨은 결합**: tm20 은 신형 머티리얼(`tm_materials` + `macro.colors.xacro`, 색상 `emeraldgreen`)을 요구. 로컬 v1.1.1 은 구형 `tmr_materials` 뿐이라 **tm20 파일만 복사하면 xacro 확장 단계에서 실패**하고, 로컬 materials 를 덮어쓰면 **기존 8종 모델이 깨진다**.
- **결정**: `tm_description` 패키지를 **v1.2.0 으로 통째 교체**. 근거(전부 직접 확인) — tm12 기준 **링크명·조인트 원점 수치 동일**(운동학 변경 아님, 색상 체계 정비일 뿐) · 업스트림이 로컬의 **상위집합**(소실 파일 0) · git 이력상 로컬 `tm_description` 은 **최초 임포트 1회, 수정 0** · 소비자는 벤더 패키지뿐(커스텀 코드 미사용).
- **MoveIt 설정**: `tm20_moveit_config` 를 **업스트림 원본명 유지**로 추가(벤더 코드 **0줄 수정**). 로컬 규약(`tm_moveit_config_tm12`)으로 rename 하려면 패키지명 참조 **13군데**를 고쳐야 해 기각.
- **실물 대조 검증**(읽기 전용 `ask_item`, 무이동): 실물 `DHTable` vs tm20 nominal → **링크 길이·각도 차이 0건**(165.2 / 636.1 / 557.9 / 156.3 / 106 / 113.15 완전 일치) → **TM20M 팔 운동학 = tm20 nominal** 실측 확정. 조인트 한계만 실물이 7° 넓음(J1·J6 ±277° vs ±270°) — **URDF 가 보수적**이라 안전 방향, nominal 유지.
- **한계**: TM12 와 TM20 은 nominal 링크 길이가 **동일**(둘 다 1300mm 급). 따라서 DH 대조는 TM5·TM14·TM16 을 배제하지만 **TM12 와 TM20 은 구분하지 못한다** — 구분은 메시(외형·충돌 형상)와 관성에 있다.
- ADR: `docs/adr/2026-07-13-tm20-moveit-model.md` (결정·검증·Rollback Plan·기각 대안)

## 12. 웹 스택과 공존하는 MoveIt 기동 (web_gui.sh 7종으로)
- ⚠️ **함정**: 벤더 `tm20_run_move_group.launch.py` 는 **`tm_driver` 와 RViz 를 자체 기동**한다. 웹 스택이 이미 tm_driver 를 띄운 상태에서 돌리면 **§4 의 중복 기동 사고가 그대로 재현**된다.
- **해결**: `tm20_move_group_only.launch.py` 신설 — `move_group` + `robot_state_publisher` + `static_tf` 만 띄우고 tm_driver·RViz 제외, 이미 떠 있는 tm_driver 의 `/joint_states`·`/tmr_arm_controller/follow_joint_trajectory` 를 재사용. 함께 `use_sim_time` 을 벤더 기본값 `True` → **`False`** 로 바로잡음(`/clock` 퍼블리셔가 없는 실물 환경에 `True` 는 부적절). 벤더 launch 는 **무수정**(단독 사용 시 여전히 유효).
- **`web_gui.sh` 통합**: `SERVICES` 에 MoveIt **한 줄**(포트 없음 → pgrep 패턴으로 생존 판정, tm_driver 뒤에 붙도록 맨 끝) + `do_stop()` 에 **한 줄**. 기존 `alive()` 가 "이미 실행 중이면 건너뜀"을 하므로 **중복 기동은 구조적으로 차단**. 스택이 6종 → **7종**.
- **검증**: `start` 시 기존 6개 전부 "이미 실행 중(건너뜀)", **MoveIt 만 신규 기동**. `pgrep -x` 정확매칭으로 `tm_driver` **1개**(중복 0)·`move_group` 1개·`rviz2` 0개. 계획 성공, 웹 포트(:8000 :9090 :6189 :3000) 전부 유지.

- **증상**: 웹 GUI 에서 촬영 명령 전송 실패, 조그 무반응. 이관 탓이 아닌지 의심.
