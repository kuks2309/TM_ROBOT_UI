# 실시간 카메라 보고서 — 한계·병목·캘리브레이션 충돌

- 작성일: 2026-07-13 (KST)
- 대상: TM(Techman) 로봇 **내장 손목 카메라**(eye-in-hand)를 통한 실시간 영상
- 결론 한 줄: **약 2 FPS(Frames Per Second)가 구조적 상한**이며, 그 이상은 **카메라 하드웨어를 바꾸지 않는 한** 의미 있게 개선되지 않는다.

## 2. 구조 — 왜 "스트리밍"이 아닌가

일반 웹캠은 초당 30장을 **계속 흘려보낸다**. TM 내장 카메라는 다르다:

```
[프레임 1장마다 이 전체가 반복된다]
PC ──Vision_DoJob 명령──▶ 로봇
                          ├─ 비전 잡 실행 (안정화 대기)
                          ├─ 카메라 노출·촬영
                          └─ 5M 픽셀 이미지를 JPEG 인코딩
   ◀──HTTP POST(약 1.5MB)── 로봇
PC ├─ 디코드(14.4MB)
   └─ /techman_image 발행 → 화면 표시
```

즉 **매 프레임이 "명령 → 촬영 → 전송 → 디코드" 왕복 전체**를 다시 수행한다. 이 왕복 시간이 곧 FPS 를 결정한다.

- 기존 GUI 의 라이브 뷰도 동일하다 — 타이머는 500ms(2 FPS 목표)로 돌지만(`main_window.py:911-928`), 왕복이 안 끝나면 다음 틱은 버려지므로 **실효 속도 = 왕복의 역수**.

## 3. 병목 실측 (2026-07-13, 무이동 연속 촬영 6회 × 2세트)

기가비트 유선(1000Mb/s, eno1) 연결, 이미지 2592×1944(5M 픽셀).

| 구간 | 시간 | 비중 | 소유 |
| --- | --- | --- | --- |
| send_script 명령 응답 | ~3 ms | 0.6% | PC↔로봇 |
| **네트워크 전송** (1.5MB) | **~13 ms** | **2.5%** | 유선 |
| PC 디코드 + 발행 | ~90 ms | 17% | PC |
| **로봇측** (안정화+촬영+인코딩) | **~410 ms** | **80%** | **로봇 내부** |
| **합계 (왕복)** | **~515 ms** | 100% | → **1.93 FPS** |

### 핵심 발견 2가지
1. **네트워크는 병목이 아니다.** 로봇이 보내는 건 raw 15MB 가 아니라 **인코딩된 1.5MB**이고, 기가비트에서 **13ms 면 전송이 끝난다**(2.5%). → "네트워크를 빠르게" 하는 개선은 무의미.
2. **병목의 80%가 로봇 내부**다. PC 코드를 아무리 최적화해도 **못 건드리는 영역**이다.

## 4. 시도한 개선과 결과

| 레버 | 근거 | 결과 |
| --- | --- | --- |
| **① 로봇 안정화 유휴 시간 축소** | [TMvision v2.18 (KR), Camera 파라미터, p.28](../Software_TMvision_2.18_1.00_KR.pdf) — "로봇이 사진을 찍기 전에 자체 조정할 수 있도록 시간을 설정" | ✅ 적용. **0.580s → 0.515s (−65ms, FPS +13%)**. 도움은 되나 **주범 아님** |
| **② 이미지 크기 축소** | 같은 문서 p.28 — "내장 카메라의 **이미지 크기**" 파라미터 존재. 기본 5M 픽셀(p.19) | ⏸ **보류** — 속도엔 유효하나 **캘리브레이션과 충돌**(§5) |
| **③ 스냅앤고(Snap&Go)** | 같은 문서 p.28 — "사진을 찍고 흐름을 계속 진행, 백그라운드에서 이미지 처리" | ⏸ 미적용. 파이프라인화로 일부 은닉 가능 |
| **④ PC 측 최적화** | — | ✅ 이미 완료(JPEG 재발행: 웹 전송 20.2MB→133KB). **하지만 병목이 아니라 체감 개선은 표시 지연에 한정** |

**결론**: 소프트웨어·설정 레버를 다 써도 **3~4 FPS 부근이 천장**이다. 로봇 내부 촬영·인코딩 시간(410ms)을 없앨 방법이 없기 때문이다.

## 5. ⚠️ 캘리브레이션과의 충돌 (가장 중요한 제약)

**해상도를 낮추면 속도는 오르지만, 이미 완료한 카메라 보정이 무효화된다.**

- 2026-07-10 에 **intrinsic(내부 파라미터) 캘리브레이션 완료** — 2592×1944 기준, 재투영 오차 **0.4575 px**(우수).
- 카메라 보정값(camera matrix: fx·fy·cx·cy)은 **해상도에 종속**된다. 해상도를 바꾸면 이 값들이 달라져 **그대로 쓰면 3D 좌표 계산이 틀어진다.**
- 즉 **속도와 정밀도가 트레이드오프** 관계다:

| 용도 | 해상도 요구 |
| --- | --- |
| **눈으로 보는 라이브 뷰** | 낮아도 무방 (사람이 보기만 함) |
| **캘리브레이션 / hand-eye / AR(Augmented Reality) 태그 정밀 측정** | **보정한 해상도와 일치해야 함** |

### 선택지
| # | 방안 | 속도 | 정밀도 | 비용 |
| --- | --- | --- | --- | --- |
| A | **풀해상도 유지** (현재) | ~2 FPS | ✅ 보정 유효 | 없음 |
| B | 해상도 낮추고 **그 해상도로 재캘리브** | ~3~4 FPS | ✅ 일관 유지 | 체스보드 15장 재촬영(약 30분) |
| C | **이원화**(정밀=풀해상도 / 라이브=저해상도) | 라이브만 ↑ | ✅ | TMflow 비전 잡 2개, 복잡도↑ |
| D | **별도 스트리밍 카메라 추가** | **30 FPS** | 별도 보정 필요 | 하드웨어·장착·배선 |

## 6. 현재 구현 상태 (2026-07-13)

- **웹 GUI 라이브 뷰 구현 완료**. Vision 탭 → `▶ 라이브 시작`.
  - **무이동 촬영**(`Vision_DoJob`) 사용 → **로봇이 움직이지 않는다** → 모션 안전 게이트 불필요.
    - 근거: [TMscript v2.18 Rev1.0, §13.26 Vision_DoJob(), p.351-352](../Programming-Language-TMscript_2.18_Rev1.0_EN.pdf) — 초기위치를 가진 잡이면 실행을 거부(False)하므로 **구조적으로 이동 불가**.
    - 실측: 연속 촬영 4회 중 TCP 최대 편차 **0.0038 mm / 0.0004°** (로봇 반복정밀도 노이즈 범위) = 실이동 없음.
  - **자가 클럭(self-clocking)**: 고정 타이머로 쏘면 왕복(~0.5s)보다 빨라 요청이 적체되므로, **프레임이 도착하면 다음 촬영을 예약**해 항상 달성 가능한 최대 속도로 수렴하게 했다.
  - 화면에 **실측 FPS** 를 표시한다.
- 기존 `📷 촬영 (이동)` 버튼(`Vision_DoJob_PTP`)은 로봇을 촬영 위치로 **이동**시키므로 **모션 게이트 유지**.

## 7. 권고

1. **단기**: 현재 구조(약 2 FPS)로 **모니터링 용도는 충분**하다. 정밀 작업(캘리브·hand-eye)이 진행 중이므로 **풀해상도 유지(방안 A)** 를 권고한다.
2. **속도가 실제 업무에 병목이 되면**: 방안 B(저해상도 + 재캘리브)로 3~4 FPS 확보.
3. **30 FPS 급 실시간이 요구사항이면**: 방안 D(별도 스트리밍 카메라)가 **유일한 해법**이다. 소프트웨어로는 도달 불가함을 분명히 한다.

## 부록 — 측정 방법 (재현 가능)

무이동 촬영을 연속 호출하며 `send_script` 전송 시각 ~ `/techman_image` 수신 시각을 측정하고, `eno1` 의 `rx_bytes` 증분으로 실제 전송량을 잰다. (로봇 무동작이라 안전)

```
평균 왕복      : 0.515s  → 이론 최대 1.94 FPS
최소/최대 왕복 : 0.454s / 0.707s
평균 전송량    : 1537 KB (인코딩된 파일)
연속 6장 총 3.11s → 실측 지속 1.93 FPS
```
