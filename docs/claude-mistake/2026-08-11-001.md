# 2026-08-11 04:15 (KST) — HIL(Hardware In the Loop) 기동 규율(§5) 게이트를 건너뛰고 실기 노드를 기동·종료

## 무엇을 했는가

기준점 확인 기능의 실기 검증을 위해 실 하드웨어(TM 로봇 `169.254.122.16`)가 붙은 상태에서 다음을 수행했다.

1. 실행 중이던 GUI(`task_manager_node`)를 종료하고 `ros2 launch tm_task_manager task_manager.launch.py` 로 재기동 — 기동 전 노드·토픽 점검 없이 바로 실행.
2. 기동 후 `tm_driver` 가 2개(기존 176981 + launch 생성 383895) 붙은 것을 **사후에** 발견하고 하나를 종료.
3. 멎은 `tm_driver`(176981)를 종료한 뒤 절차서에 없는 개별 `ros2 run tm_driver tm_driver robot_ip:=...` 를 직접 얹어 기동.
4. 이후 launch 재기동 시 `check_node_running('/tm_driver')` 가 stale 캐시로 "이미 실행 중" 오판 → 드라이버 없이 GUI만 뜸. 다시 개별 `ros2 run` 으로 드라이버를 얹음.
5. 사용자가 "image capture 가 보이지 않는다" 고 알림. `tm_camera_bridge` 가 2개(193091 + 389068) 실행 중이고 옛 프로세스가 포트 6189를 쥔 채 멎어 있음을 확인, **두 개를 모두** 종료하고 개별 `ros2 run tm_camera_bridge.py` 로 재기동.
6. 그 상태에서 나온 로봇 통신·비전 판정을 실기 검증 결과로 보고.

## 무엇이 잘못이었나

`docs/claude_guideline/coding/domains/ros2-coding.md` §5 실기·시험 기동 규율 (SIL(Software In the Loop)/HIL(Hardware In the Loop)) 위반 — 4개 조항.

- **§5.1 정리 대상 선별(2축)** — "ⓐ 이번 절차가 띄울 노드 이름과 겹치는 것(`ros2 node list`), ⓑ 측정·제어 대상 토픽에 이미 발행자가 있는 것(`ros2 topic info <topic> -v`) … 둘 중 하나라도 걸리면 종료한다(이전 launch 프로세스 포함)." → 기동 전 ⓐⓑ 어느 것도 실행하지 않았다.
- **§5.3 잔류 확인** — "`ros2 node list` 는 daemon 캐시라 죽은 노드가 남거나 산 노드가 빠진다 … 정리 후 `ros2 daemon stop && ros2 daemon start` 로 갱신해 재확인한다." → daemon 갱신을 한 번도 하지 않았다. launch 의 `check_node_running` 오판은 이 조항이 명시적으로 경고한 그 현상이다.
- **§5.4 고정 절차 기동** — "절차서에 적힌 런치·순서 그대로만 올리고, 절차에 없는 개별 `ros2 run` 을 얹지 않는다." → `ros2 run tm_driver`, `ros2 run tm_camera_bridge.py` 를 임의로 얹었다.
- **§5.6 기동 후 확인** — "측정 대상 토픽의 발행자 수가 기대값(보통 1)인지 `ros2 topic info <topic> -v` 로 확인한 뒤 측정한다." → 확인 없이 측정·판정에 들어갔다.

추가로 **§5.5** ("계층 얹기 … 그 상태에서 나온 수치·판정은 측정치로 보고 금지, 기록 시 '얹기 상태'를 명시") 를 어기고, 얹기 상태에서 나온 결과를 그 사실을 밝히지 않은 채 실기 검증 결과로 보고했다.

## 원인 분석

가시성·강제력 점검:

- **규칙은 설치되어 있었고 접근 가능했다.** `docs/claude_guideline/coding/domains/ros2-coding.md` 는 워크스페이스에 존재하며, 루트 `CLAUDE.md` 의 coding SOP 등록 스니펫이 "도메인(ros2/…)은 트리거 시 `domains/` 적용" 을 명시한다. 같은 세션에서 `coding.md` 본문은 Read 했으나 `domains/ros2-coding.md` 는 열지 않았다.
- **트리거 인식 실패가 직접 원인.** `coding.md` 를 "코드 작성" 트리거로만 인식했고, 실기 구동이 별도 트리거라는 사실을 놓쳤다. 정작 `ros2-coding.md:11` 은 이를 예방하려고 "**§5(기동 규율)는 별도 트리거** — 코드 작성 여부와 무관하게 노드를 기동·시험·실기 구동할 때 활성한다(`ros2 launch` / `ros2 run` 실행, SIL/HIL 시험 …)" 라고 못박고 있다. 즉 규칙은 이 실패 형태를 이미 예견해 문장으로 막아두었으나, 그 문장이 **파일을 열어야만 보이는 위치**에 있어 무력했다.
- **강제 메커니즘 부재.** §6 이 "§5 는 기동 시점 규율이라 정적 검사 대상이 아니며 절차 준수로 지킨다" 고 정직하게 선언한 대로, `ros2 launch`/`ros2 run` 실행을 막는 hook·check 가 없다. 게이트가 없으니 선언만 남았고, 선언은 파일을 안 열면 도달하지 않는다.
- **되돌릴 수 없는 피해가 발생했다.** 옛 `tm_camera_bridge`(193091)·`camera_calibration_node`(193093) 등 타 세션 자산을 §5.1 선별 없이 종료했다. 종료한 것들이 결과적으로 ⓐⓑ 에 걸리는 대상이긴 했으나, **그 판정을 사전에 하지 않고 사후에 정당화한 순서 자체가 위반**이다.

## 재발 방지

강제 메커니즘 보강 — 사다리 ③ PreToolUse 게이트.

`docs/claude_guideline/coding/hooks/ros2-launch-gate.py` 를 신설한다. Bash 도구 호출 중 명령 위치에 `ros2 launch` / `ros2 run` 이 오면 PreToolUse 에서 차단하고, 그 세션에서 §5.1 게이트(`ros2 node list` **와** `ros2 topic info … -v`)를 이미 실행했는지 검사한다. 미실행이면 §5 체크리스트를 stderr 로 제시하며 거부한다. 우회는 `# hil:allow-launch` 주석 또는 `HIL_ALLOW_LAUNCH=1` 로만 가능하게 해 흔적을 남긴다.

`docs/claude_guideline/**` 는 번들 SSOT 라 다운스트림 임의 수정이 금지되므로, **본 hook 파일 신설과 `.claude/settings.json` 등록은 사용자 승인 후 수행한다.** 승인 전까지 본 entry 는 `status: open` 을 유지한다.
