# 2026-08-31 15:20 (KST) — `ip addr` 의 인터페이스 1개를 "RJ45 포트 1개" 로 단정하고 4번 랜포트를 공유기 포트로 추측

## 무엇을 했는가

사용자가 "원격컴(nx-orin-1)에 연결된 컴이 있는지 확인" 을 요청하고 "4번 랜에 크로스 케이블로 연결해두었음" 이라고 덧붙였다. orin 에서 `ip -br addr` 로 `eth0` 하나만 보이는 것을 근거로 첫 답변에 **"orin 은 RJ45 가 1개뿐이고 로봇에 직결"** 이라고 단정했고, 이어 "4번 랜" 을 TM 제어박스 포트 또는 **현장 공유기(192.168.44.1)의 LAN 4번 포트**로 추측해 공유기망 192.168.44.0/24 를 스윕·보고했다.

## 무엇이 잘못이었나

- OS 가 보는 네트워크 인터페이스 수(1) 를 물리 포트 수(1) 로 검증 없이 등치했다. 실제 기기는 Neousys NRU-52S(+) 로, **PoE++ 포트 4개가 내장 L2 스위치를 거쳐 단일 `eth0` 에 묶이는 구조**다 — 데이터시트 각주 [1]: "A single network (eth) with L2 layer switch that allows to have multiple PoE ports, but all on the same network." [Neousys NRU-52S+/NRU-52S Datasheet (Last updated 6 Nov 2025), footnote [1], page 2](references/neousys/nru-52s/nru-52s_datasheet.pdf). 사용자의 "4번 랜포트" 는 그 상자의 실재 포트였다.
- 잘못된 전제 위에서 "공유기 포트" 라는 2차 추측을 세워 무관한 망을 스윕했고, 사용자가 이를 교정해야 했다(정정 라운드 1회 낭비).

## 사용자 지적

> "공유기가 아니라 원격 PC에 직접 연결헀다구요"

(직전 두 메시지 "4번 랜에 연결해두었음 크로스 랜 케이블로", "4번 랜포트에 연결했는데" 도 같은 사실을 반복 전달한 것이었다.)

## 원인 분석

category `wrong-assumption` — 환경(하드웨어) 동작을 검증 없이 가정.

`/proc/device-tree/model` 이 `NRU-50_2025-02-17_1116` 으로 기종을 그대로 노출하고 있었고 한 번의 `cat` 으로 확인 가능했음에도, 인터페이스 목록만 보고 물리 구성을 추론했다. "NIC 1개 = 포트 1개" 는 데스크톱 PC 에서는 대개 맞지만 산업용 임베디드 박스(내장 스위치·PoE 허브)에서는 성립하지 않는 가정이며, 이 구분을 의식하지 못했다. 사용자가 두 번 "4번 포트" 를 말했을 때도 "그 포트가 존재하는가" 를 기기 사양에서 확인하는 대신 내 전제를 지키는 방향(공유기·제어박스)으로 해석을 옮겼다.

## 재발 방지

지식·컨텍스트 보강 (`mistake` 형):

1. 메모리 `tm-robot-deploy-topology.md` 에 orin 하드웨어 사실을 추가했다 — 기종(NRU-52S(+), NRU-50 시리즈), **PoE++ 4포트 = 내장 L2 스위치 = 단일 eth0**, 로봇이 그중 한 포트, sudo 비밀번호 필요(BatchMode 로 arp-scan 불가), 현장 Windows PC 와 orin 이 같은 공인 IP. 이 메모리는 MEMORY.md 인덱스를 통해 매 세션 시작 시 주입된다.
2. 1차 source 를 `references/neousys/nru-52s/` 에 보관했다(데이터시트 2p + 사용자 매뉴얼 v1.4 20p, `pdftotext` 추출본 동봉). 이후 이 기기의 I/O 관련 주장은 여기서 인용한다.
3. 판단 원칙(메모리에 함께 기록): 원격/임베디드 기기의 **물리 포트·슬롯 수를 말하기 전에 `/proc/device-tree/model`(또는 `dmidecode`) 로 기종을 확인하고 벤더 사양을 대조**한다. 인터페이스 목록은 OS 관점일 뿐이다.
