# 2026-07-08 17:00 (KST) — 검증 curl 이 라이브 로봇을 실제로 움직여 경고음 유발

## 무엇을 했는가
tm_web_bridge(증분 2)의 `/jog` 엔드포인트를 curl 로 검증하면서 실제 jog 요청을 5건 전송했다:
- `POST /jog {axis:x, direction:1, step_mm:10, velocity:20}` → 성공 응답 "X+10.0mm 이동"
- `POST /jog {axis:rx, direction:-1, step_mm:9999, velocity:999}` → clamp 후 "RX-100.0deg 이동 (속도 100%)" 성공 응답
잘못된 axis/direction 거부와 clamp 동작을 확인할 의도였으나, 정상 요청(#2·#5)은 브리지가 `set_positions` 로 **실제 로봇에 모션 명령을 전송**했다.

## 무엇이 잘못이었나
로봇이 라이브 상태(tm_driver 기동·`/tool_pose` 발행)임을 재확인하지 않고, 되돌릴 수 없는 물리 동작(로봇 모션) 명령을 자동 검증 과정에서 전송했다. 특히 극단값 테스트가 clamp 되어 Rx -100° / 100% 속도라는 크고 빠른 회전 명령이 되었고, 로봇이 관절 한계/속도 관련 안전 경고음을 냈다. 사용자가 로봇 전원을 차단했다.

## 사용자 지적
> "너가 뭘 해갖고 로봇 자체에서 경고음이 계속 들리길래 지금 로봇 전원을 꺼버렸음 무슨 일이었던거임?"

## 원인 분석
category: `wrong-assumption`. 약 10분 전 `ros2 node list` 에서 tm_driver 가 안 보였다는 **stale 한 관찰**을 근거로 "로봇 오프라인"이라 가정하고, 모션 명령 직전에 로봇 라이브 상태를 재확인하지 않았다. 실제로는 사용자가 그 사이 tm_driver 를 기동해 로봇이 라이브였다. 자동 검증(curl)으로 물리 모션을 직접 유발하는 것의 위험을 과소평가했다.

## 재발 방지
- **지식 보강**: 메모리 `robot-live-before-motion.md` 신설 — (1) 모션 명령 직전 반드시 `/robot/status`·`/tool_pose` 로 라이브·안전 상태 재확인, (2) 라이브 로봇 상대로 jog/모션 엔드포인트를 curl/자동 검증하지 말 것(더미/시뮬 또는 사용자 입회 하 수동 확인), (3) 극단값 테스트라도 clamp 결과가 실동작이면 위험.
- **설계 문서 안전절 보강**: connection-design §안전에 "검증은 로봇 미기동 상태에서, 실모션은 사용자 입회+저속" 명시.
- **코드 하드닝 제안(사용자 승인 대상)**: 회전축 별도 clamp(≤ small deg), 기본 속도 상한 하향, `/jog` 에 motion-enable 게이트(기본 비활성) 추가.
