# 2026-08-15 15:05 (KST) — 기존 generate_runtime 상대좌표 워크플로우를 조사하지 않고 오프셋 체인 초안 작성

## 무엇을 했는가

"마커 1개 측정 → 마커 4개 위치로 이동 → 4개 측정 저장" 레시피 초안 요청을 받고, `RecipeManager.JOB_TYPES` 와 `job_executor._execute_job` 분기를 훑은 뒤 다음 2개를 작성했다.

- `config/recipes/pallet0_cali_auto.yaml` — `find_landmark` 격자 탐색으로 드로어 마커에 정렬 후, `save_pose`/`move_to_saved_pose` 앵커 복귀 + `move_linear` 고정 오프셋으로 4점 순회
- `config/recipes/drawer_offset_teach.yaml` — 조그 티칭으로 절대좌표 P0~P4 를 받아 적고 **사람이 뺄셈**해 오프셋을 구하는 취득용 레시피

아울러 `move_linear` 가 쓰는 `Move_Line("TPP", ...)` 의 기준 좌표계가 베이스인지 공구인지 확정할 수 없다며, 사용자에게 실기 실험(저속 50mm 이동 후 TCP 확인)을 제안했다.

## 무엇이 잘못이었나

두 초안이 풀려던 문제 — 랜드마크 1점 측정 후 고정 오프셋으로 여러 점을 찍는 것 — 는 이 저장소에 **이미 구현·운용 중인 워크플로우**였다.

- `generate_runtime` Job → `tools/convert_to_runtime.py:150` `RecipeConverter.convert_to_relative` 가 `scan_tm_landmark` 이후의 모든 좌표 Job 을 `T_landmark⁻¹ @ T_abs` 로 변환한다 (`convert_to_runtime.py:265`)
- 런타임 실행 시 `job_executor._transform_relative_to_absolute` (`job_executor.py:343-349`) 가 `T_landmark @ T_rel` 로 복원한다
- 기준점은 `main_window._update_recipe_reference` (`main_window.py:753-760`) 가 저장 시 `reference.tm_jig_landmark` 에 자동 기록한다
- 동작하는 실물 예시가 2쌍 있다: `tm_landmark_test4.yaml` ↔ `tm_landmark_test4_runtime.yaml`, `gripper_test_jig.yaml` ↔ `gripper_test_jig_runtime.yaml`

그 결과 초안 2개가 전부 폐기 대상이 되었고, 사용자에게 **불필요한 수작업 2건**을 요구했다 — (1) 절대좌표 5점 티칭 후 손 뺄셈, (2) TPP 좌표계 확정을 위한 실기 실험. 기존 경로를 썼다면 변환이 자동이라 둘 다 필요 없다.

## 사용자 지적

> "멀리서 찍기 -> 고정 오차로 4점 찍기인데...."

이 한 줄로 `find_landmark` 격자 탐색이 요구사항이 아니었음이 드러났고, 그 확인 과정에서 `docs/vision_base_commands.md` → `tm_landmark_test4_runtime.yaml` → `convert_to_runtime.py` 순으로 기존 워크플로우가 발견되었다.
