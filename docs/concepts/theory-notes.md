## 1. 프론트엔드 vs 백엔드

**비유 (식당)**: 프론트엔드 = 손님이 보는 홀·메뉴판·주문받는 직원. 백엔드 = 주방(요리·재료). 손님(브라우저)은 주방에 직접 못 들어가고 직원(브리지)을 통해 주문.

- **프론트엔드(Frontend)** = 사용자가 **보고 만지는** 부분. 브라우저에서 도는 화면·버튼·입력. 이 프로젝트에선 React 앱(`~/Desktop/TRobotics_Client`). 로봇을 직접 못 만지고 화면만 그림.
- **백엔드(Backend)** = 눈에 **안 보이는 서버·로직**. 데이터·하드웨어 연결 담당. 이 프로젝트에선 `tm_web_bridge`(FastAPI) + ROS2(Robot Operating System 2).
- **대화 방법**: HTTP(HyperText Transfer Protocol)의 `fetch`(요청/응답)나 WebSocket(실시간).
- **예**: `GET /robot/status` → 백엔드가 로봇 위치를 읽어 제공 → 프론트가 0.3초마다 받아 화면 표시.

## 2. 브리지란? (웹 ↔ 로봇 통신)

브리지의 본질은 **프로토콜 통역기이자 실제 연결 주체**다. IP 주입은 목적이 아니라 결과.

- **왜 필요**: 브라우저는 HTTP/WebSocket만 할 수 있고, 로봇/ROS2는 DDS(Data Distribution Service)·raw TCP(Transmission Control Protocol)만 알아듣는다. 둘은 직접 대화 불가 → 중간 통역사가 필요.
- **하는 일 3가지**: ① 프로토콜 번역(WebSocket ↔ ROS2 토픽/서비스), ② 로봇 연결을 실제로 보유(그래서 로봇 IP도 브리지가 앎), ③ 데이터 가공·중계.
- **IP 위치의 의미**: 브라우저는 로봇에 직접 안 붙으니 로봇 IP를 몰라도 됨. 실제로 붙는 브리지가 IP를 관리.

## 3. 웹 GUI가 로봇에 연결되는 구조 (하이브리드)

```
[브라우저(React)]
   ├─ roslibjs ──ws:9090──▶ [rosbridge_server]  ← 실시간 상태/영상(구독)
   └─ fetch ────http:8000─▶ [tm_web_bridge(FastAPI+rclpy)] ← Job/모션/IO(명령)
                                   └─ ROS2 서비스 ──▶ [tm_driver] ──▶ [로봇]
```

- **왜 브라우저가 로봇에 직접 못 붙나**: 브라우저는 보안상 raw 소켓을 못 연다(HTTP/WebSocket만). TM 로봇은 raw TCP(5890 Listen 명령 / 5891 상태) + ROS2로만 접근.
- **rosbridge**: WebSocket ↔ ROS2 통역(표준). 실시간 구독(관절·TCP·IO)에 사용.
- **FastAPI 브리지**: 기존 파이썬 로직(job_executor·recipe_manager·teaching_service)을 재사용해 Job 실행·모션·IO를 REST(Representational State Transfer)로 노출.
- **하이브리드**: 실시간은 rosbridge, 명령/로직은 FastAPI — 각 강점을 씀.

## 4. 원격 접속 (localhost vs IP, 같은 네트워크)

- **`localhost`** = "이 컴퓨터 자신". 다른 기기에선 안 통함. 다른 기기는 **서버 PC의 IP**(예: `http://192.168.1.10:3000`)를 써야 함.
- **되는 조건**: 다른 기기가 **같은 네트워크(LAN, Local Area Network)** — 같은 공유기/WiFi — 에 있어야 함. 서버 포트(3000/9090/8000)가 `0.0.0.0`으로 열려 있어야 외부 접근 가능.
- **자동 host**: 웹 GUI는 접속한 주소(`window.location.hostname`)를 따라가서, 다른 기기가 `192.168.1.10:3000`을 열면 rosbridge·브리지도 그 IP로 자동 연결 → **다른 기기는 서버 PC하고만 통신하고, 로봇 통신은 서버 PC가 대신**.
- **자주 막히는 것**:
  - **서브넷 중복**: 한 PC에 같은 대역(192.168.1.x) IP가 두 인터페이스에 붙으면 라우팅이 꼬임(응답이 엉뚱한 랜카드로 나감). → 중복 IP 제거로 해결.
  - **AP(Access Point) Isolation(단말 격리)**: 같은 WiFi여도 공유기가 기기끼리 통신을 막는 설정. 게스트 WiFi에 흔함. → 공유기에서 끄기.
  - **방화벽/ICMP**: 윈도우는 기본적으로 ping(ICMP, Internet Control Message Protocol)을 막음 → ping 실패해도 웹 접속은 될 수 있음.

## 5. 좌표계(프레임)와 Hand-Eye 보정

### 좌표계(프레임)
- 위치는 **"어느 기준"**이냐에 따라 값이 다르다. **카메라 프레임**(렌즈 기준)과 **로봇 base 프레임**(로봇 발밑 기준)은 서로 다른 좌표계.
- 로봇에 "여기로 가라"고 하려면 **로봇 base 기준** 좌표를 줘야 함.

### Hand-Eye 보정
- **정의**: 카메라가 본 위치를 로봇이 갈 위치로 바꾸기 위해, **카메라↔로봇의 위치 관계(변환)**를 알아내는 보정. (hand=로봇 손, eye=카메라 눈)
- **왜 필요**: 카메라는 "카메라 기준"으로 알려주는데 로봇은 "자기 기준"으로 움직이니, 둘을 잇는 변환이 없으면 카메라 좌표가 로봇에게 무의미.
- **두 구성**: **eye-in-hand**(카메라가 로봇 손목에 부착 — 이 프로젝트) vs **eye-to-hand**(카메라 고정).
- **어떻게**: 로봇을 여러 자세로 움직이며 (a) 로봇 위치 + (b) 카메라로 본 기준판(체스보드)을 기록 → `cv2.calibrateHandEye`로 변환 행렬 산출 → 저장 후 "카메라 좌표 × 변환 = 로봇 좌표"로 사용.
- **참고**: GUI의 "Hand-Eye Test" 탭은 보정 **계산**이 아니라, 보정된 상태의 **정밀도(반복성) 측정** 도구(별개).

## 6. AR 태그 모션 (비전 가이드)

- **AR(Augmented Reality) 태그** = 흑백 정사각 패턴(ArUco). 물체·지그에 붙이면 카메라가 3D 위치·자세를 인식. 물체가 매번 다른 곳에 놓여도 카메라가 찾아 보정하는 **비전 가이드 방식**.
- **용도**: pick & place, 정밀 조립, 지그 정렬.
- **왜 이 프로젝트에선 AR 모션이 "스텁"인가**: 카메라가 준 좌표는 **카메라 프레임**인데, 로봇 base 프레임으로 바꿀 **hand-eye 보정이 아직 없어서**. 그대로 로봇에 주면 엉뚱한 데로 감(위험) → 실제 이동 대신 로그만 남기는 스텁으로 막아둠. hand-eye 구축 시 진짜 동작(계획서: `docs/planning/hand-eye-calibration-plan-2026-07-08.md`).
- **현재 동작하는 AR 경로**: `scan_ar_tag` → 로봇 내부 TMflow 비전이 이동을 담당(PC가 좌표 계산 안 함).

## 7. IO 제어 (Digital IO)

- **IO(Input/Output)** = 로봇이 바깥 세상(그리퍼·센서·컨베이어·램프)과 주고받는 **전기 신호**. 팔의 "움직임"과 별개.
- **DI(Digital Input)**: 바깥 → 로봇. 로봇이 **읽는** 신호(센서 감지, 버튼). → 읽기 전용.
- **DO(Digital Output)**: 로봇 → 바깥. 로봇이 **켜는/끄는** 신호(그리퍼 잡기, 램프). → 쓰기 = actuation.
- **Digital vs Analog**: 디지털 = 켜짐/꺼짐 2가지. 아날로그(AI/AO) = 0~10V 같은 연속값(압력·거리).
- **두 모듈**: **Control Box(제어박스, 발밑, 핀 16개)** — 외부 장비. **End Effector(엔드이펙터, 팔 끝, 핀 4개)** — 보통 **그리퍼**가 여기.
- **왜 중요**: 실제 작업은 "이동 → 그리퍼 닫기(DO) → 이동 → 센서 확인(DI) → 그리퍼 열기(DO)"처럼 **모션 + IO가 섞여** 돌아감. IO 없이는 집고 놓기가 안 됨.

## 8. 모션 안전 게이트

- **개념**: 로봇을 실제로 움직이는 명령(jog·시퀀스 실행·DO 쓰기)은 **기본적으로 차단**해 두고, 상단 "모션 활성" 스위치를 명시적으로 켰을 때만 나가게 하는 안전장치.
- **왜**: 2026-07-08, 검증 중 과속 명령(Rx 100°/100%)이 라이브 로봇을 움직여 안전정지·복구 사건 발생. 재발 방지로 ① 게이트(기본 꺼짐) ② 속도 clamp(jog ≤30%, 회전 ≤10°, 시퀀스 velocity ≤30%) ③ 정지 버튼 ④ 화이트리스트를 도입.
- **원칙**: 실모션 검증은 **사용자 입회 + 저속 + 소량**으로만. (사건 기록: `docs/claude-mistake/2026-07-08-001.md`)

## 9. 카메라 캘리브레이션 — 왜/효과/가능해지는 작업

### 캘리브레이션이 필요한 이유 (두 가지 문제를 푼다)
1. **렌즈 문제 → Intrinsic(내부) 보정**: 카메라 이미지는 렌즈 왜곡이 있어(직선이 휘고 가장자리가 늘어남) 픽셀 좌표가 실제 방향·거리로 곧바로 매핑되지 않는다. 초점거리·광학중심·왜곡계수를 모르면 "이 픽셀 = 실제 어느 방향/얼마나 먼가"를 계산할 수 없다. 체스보드로 이 값들을 알아내는 게 intrinsic 보정.
2. **좌표계 문제 → Hand-Eye(외부) 보정**: 카메라는 "카메라 기준", 로봇은 "base 기준"으로 말한다. 둘을 잇는 변환이 없으면 카메라 좌표는 로봇에게 무의미(→ [§5](#5-좌표계프레임과-hand-eye-보정)).

즉 캘리브레이션 = **"카메라가 본 것을 실제 물리 세계(그리고 로봇)의 값으로 신뢰할 수 있게 만드는 것"**.

### Intrinsic(내부 파라미터)이란?
- **정의**: 카메라가 어디 놓이든 상관없는 **렌즈+센서 고유 특성**. (반대 = extrinsic/외부 = 카메라가 어디 있나 → hand-eye)
- **비유**: 안경 도수 처방. 그 렌즈만의 광학 "처방전"이라 렌즈·줌 안 바꾸면 안 변함 → **카메라당 1회**만 구하면 됨.
- **구성 3가지**: ① 초점거리(얼마나 줌—픽셀 간격↔각도) ② 광학중심(광축이 센서에 닿는 실제 중심) ③ 왜곡계수(직선이 휘어 보이는 정도, 특히 가장자리). → 묶으면 camera matrix(3×3)+왜곡 벡터.
- **왜 ①번 먼저**: intrinsic 없으면 "이 픽셀=실제 어느 방향/거리"를 못 구해 마커 3D 자세가 애초에 틀어짐. hand-eye(②)는 그 위에 로봇 연결이라 intrinsic이 부정확하면 무의미 → 순서는 intrinsic→hand-eye.

### 효과 (무엇이 좋아지나)
- **Intrinsic 후**: 왜곡이 제거된 이미지, 픽셀→실제 방향이 정확, 마커 3D 자세(`solvePnP`) 신뢰 가능, 거리·크기 측정이 맞아짐.
- **Hand-Eye 후**: 카메라가 본 위치를 로봇이 **정확히 실행**할 수 있음(카메라 좌표 × 변환 = 로봇 좌표).

### 캘리브 수준별 "가능해지는 작업"
| 캘리브 수준 | 가능한 것 | 이 프로젝트 상태 |
| --- | --- | --- |
| **없음** | 카메라 영상 **"보기"(모니터링)** 만. 좌표값은 신뢰 못 함 | 현재 (Vision 탭 표시) |
| **Intrinsic 만** | 마커/물체의 카메라 프레임 **3D 자세 측정**, 시각 검사, 왜곡보정 영상 | 노드 구현됨(실행하면 가능) |
| **Intrinsic + Hand-Eye** | **비전 가이드 모션**: AR 태그 추종(`move_to_ar_offset`/`align_to_ar_tag`/`move_to_ar_center`), 비전 pick & place, 검출 위치로 정밀 접근·정렬 | Hand-Eye 미구현(계획서만) |

- **정밀도 기대치**: eye-in-hand + 단일 마커는 통상 **±1~3 mm**(마커 크기·거리·해상도 의존, 계획서 §11). 더 정밀하려면 마커↑/거리↓/다중마커/힘제어 병행.
- **핵심 요약**: 지금은 "눈으로 보기"만 되고, 캘리브(intrinsic→hand-eye)를 하면 **"본 것을 로봇이 집고 옮기고 맞추는"** 작업이 열린다. AR 태그 잡들이 스텁인 것도 이 때문(→ [§6](#6-ar-태그-모션-비전-가이드)).

### 이 프로젝트의 체스보드 스펙 (코드 기준)
`config/calibration_params.yaml`: 내부 코너 **9×6**(=물리 **10×7 칸**), 사각형 **25 mm**. 카메라는 손목 부착(eye-in-hand)이라, 체스판을 고정하고 로봇을 여러 자세로 움직여 촬영한다.
